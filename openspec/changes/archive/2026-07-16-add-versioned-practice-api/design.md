## Context

JapaFlow is adding a new practice experience for Japanese lessons. The current preview stores generated practice data in static files and user submissions in localStorage, but the intended product needs backend persistence for user attempts and cross-device practice state. This change is intentionally separate from the older `/lesson/{N}/exercises` practice implementation.

The new practice content is generated by prompt and already behaves like a rich document model: a lesson contains activities, each activity can contain layout, assets, examples, item groups, and many item answer shapes. User submissions happen at the activity level, but each activity contains several small exercise items whose right/wrong results are valuable for future analytics.

Implementation is split across repositories. The Java backend codebase owns MySQL schema changes, migrations, authentication/user resolution, persistence services, and `/api/japaflow` practice endpoints. This repository owns the practice frontend adapter, local preview behavior, and any local Node proxy/development support needed to call those backend endpoints.

## Goals / Non-Goals

**Goals:**

- Store generated lesson practice content as versioned publishable data.
- Expose published practice content through authenticated learner APIs.
- Record every activity submission as an append-only attempt.
- Record each item result inside an activity attempt for future wrong-item analysis.
- Track resumable user progress separately from immutable attempt history.
- Keep the data model extensible for analytics and a wrong-exercise playground.

**Non-Goals:**

- Replace the older lesson exercise implementation in this change.
- Build analytics dashboards or the wrong-exercise playground in the first implementation.
- Normalize every prompt-generated content field into relational tables.
- Run AI generation from the backend as part of the first implementation.

## Decisions

### Store Practice Content as Versioned JSON

Practice content will be stored in a `practice_set` table with `lesson_id`, `version`, `status`, and `content_json`.

Rationale: generated practice content contains heterogeneous layouts, assets, audio metadata, grouped items, and answer structures. Storing the whole `LessonPractice` document as JSON avoids premature normalization and allows the prompt-generated schema to evolve.

Alternative considered: normalize activities, groups, items, prompts, assets, and answers into many relational tables. This would improve SQL-level querying of content but adds large schema surface area before the content model stabilizes.

Decision: use JSON content for MVP, and require stable IDs plus immutable published versions so user attempts remain meaningful.

### Split Implementation Across Repositories

The OpenSpec change defines one product contract, but not all implementation work lives in this repository.

Rationale: the existing app uses `/api/japaflow` as the authenticated backend surface, and those Java APIs plus database migrations live outside this frontend/static Node repository. Making ownership explicit prevents the frontend work from appearing complete before the backend contract exists.

Alternative considered: implement temporary persistence in this repo's Node server. That would help local demos but would not solve the real authenticated cross-device persistence requirement.

Decision: Java backend tasks are external implementation tasks that must be completed or provided by the user. This repo should integrate against the agreed API contract and can keep local fallback behavior only as a development/offline path.

### Use Append-Only Attempt History

Each submission of one main practice activity will create one `practice_activity_attempt` row and multiple `practice_item_attempt` rows.

Rationale: current UI behavior submits a main question/activity containing multiple small exercises. Analytics and future wrong-exercise replay need the item-level record, while submission timing, duration, and aggregate score belong to the parent activity attempt.

Alternative considered: store only the latest state per activity. That is simpler for resume behavior but loses historical attempts and cannot answer questions such as which exercise types are repeatedly wrong.

Decision: append attempts and never overwrite them. Use a separate progress/session table for current UI state.

### Make Item Attempts the Analytics Unit

`practice_item_attempt` will include `interaction_type`, `answer_unit`, `evaluation_mode`, `user_answer_json`, `correct_answer_json`, `is_correct`, `score`, and optional `error_tags_json`.

Rationale: future summaries need to group failures by item, interaction type, answer unit, and generated content version. Correct-answer snapshots make historical review stable even if a newer practice set version changes content.

Alternative considered: store item IDs and correctness only. That supports simple wrong counts but is too weak for explaining mistakes or replaying wrong exercises.

Decision: save enough metadata to support future analytics without requiring the future features to exist now.

### Use Client Attempt IDs for Idempotency

The submit API will require or generate a `client_attempt_id` and enforce uniqueness per user/practice activity.

Rationale: network retries can duplicate POST requests. Duplicate attempt rows would corrupt analytics and confuse progress state.

Alternative considered: allow duplicate rows and deduplicate later. That pushes correctness problems into every analytics query.

Decision: the backend must treat repeated submissions with the same client attempt ID as the same attempt result.

### Keep Session Progress Separate

`practice_session` will store resumable UI progress such as current activity, completion counts, status, and last active time.

Rationale: attempt history is an audit log; session progress is a mutable view optimized for continuing practice. Keeping them separate prevents analytics history from being rewritten when the user resumes, resets, or navigates.

Alternative considered: derive all progress from attempts on every load. That is accurate but can become expensive and does not capture non-submission UI state such as current activity.

Decision: maintain session progress as a mutable summary, updated by submissions and explicit progress APIs.

## Risks / Trade-offs

- [Risk] JSON practice content makes SQL queries over content harder. -> Mitigation: copy query-critical metadata such as `activity_id`, `item_id`, `interaction_type`, `answer_unit`, and `evaluation_mode` into item attempt rows.
- [Risk] Prompt-generated IDs could change between versions. -> Mitigation: published practice sets are immutable, and changed generated content creates a new practice set version.
- [Risk] Correctness calculated on the client could be tampered with. -> Mitigation: MVP can accept client results for speed, but the API contract preserves correct-answer and evaluation metadata so backend validation can be added later.
- [Risk] Attempt history can grow quickly. -> Mitigation: index by user, lesson, practice set, activity, item, and submitted time; add retention or aggregation only when usage warrants it.
- [Risk] Resetting progress could be mistaken for deleting history. -> Mitigation: reset only mutates session/progress records; attempt history remains append-only.

## Migration Plan

1. Confirm the Java API repository path, migration tooling, auth/user-id extraction pattern, and standard response envelope.
2. In the Java backend codebase, add new database tables for practice sets, sessions, activity attempts, and item attempts.
3. In the Java backend codebase, add APIs for published content, session load/update/reset, and activity submission.
4. In this repository, update the new practice frontend adapter to read from the Java backend and submit activity attempts.
5. Keep the older exercise implementation unchanged until the new practice system has been validated.
6. Rollback by disabling the new practice routes or returning to static preview/localStorage; append-only attempt tables can remain unused.

## Open Questions

- Should the first implementation accept client-side grading, or should the backend re-grade exact/choice answer types immediately?
- Should practice content authoring APIs live under the learner service or a separate admin-only surface?
- Should local anonymous attempts be importable after login in the first implementation, or deferred until after basic persistence is working?
- What is the exact Java backend repository path and migration framework to use for implementation?
